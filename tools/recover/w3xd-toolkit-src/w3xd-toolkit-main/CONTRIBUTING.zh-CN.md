## 三条底线

这三条不是风格偏好。违反其中任何一条的 PR，代码写得再好也无法合并。

### 1. 绝不提交游戏数据、密钥或反编译出的游戏内容

本仓库**不含任何暴雪内容**，必须保持这样。请不要提交包含以下内容的 PR：

* `.w3x`、`.w3m`、`.w3n`、`.w3xd`、`.mpq`、`.luac` 文件，或任何 `*.files/` 目录下的内容；
* 导出的素材 —— 模型、贴图、音频、地形、字符串表；
* **从正式地图反编译出的 `war3map.lua`。** 那是暴雪的源代码，提交它会把本仓库变成它的分发点；
* **license 值或派生出的 AES 密钥。** 你的值是账号绑定的，公开它等于让别人能解开你的容器。
  在 issue 里粘贴同样不行；
* 内存转储、可执行文件大段的反汇编清单，或任何暴雪二进制文件。

`.gitignore` 挡住了常见扩展名，但那只是兜底，不是「可以试一下」的许可。
如果你不确定某个东西能不能放进来，先开个 issue **用文字描述**它。

**可以**随时包含的：偏移、大小、字段布局、少量指令片段（为说明问题引几行）、
算法描述，以及你自己生成的合成测试数据。

### 2. 不引入新的运行时依赖

`w3xd-toolkit` 用 `pip install -e .` 安装时**不拉任何东西**。AES、CCM、GF(2) 求解器
和 MPQ 读取器全部在仓库内实现，Windows CNG 只是可选的加速路径而非必需。
引入必需第三方包的 PR 会被要求去掉；放在 `[project.optional-dependencies]` 下的
开发工具类可选项没问题。

项目唯一使用的外部工具 unluac 由脚本在运行时拉取，不会 vendor 进仓库。

### 3. 任何改动格式的修改都必须附带离线测试

测试套件自己合成容器和 MPQ 归档并对其断言。对解析、加密或转码的改动，
必须附上同样风格的测试 —— 在干净检出、没有任何游戏文件的情况下就能跑通。

只在「你磁盘上恰好有张地图」时才通过的测试会被拒绝，「我手动验证过了」也一样。
如果你没法用合成数据表达你的场景，请在 PR 里说明，我们一起想办法。

## 最需要什么

大致按有用程度排序：

1. **格式文档的更正。** 如果某个字段写错了或漏了细节，这是价值最高的贡献。
   请附证据 —— 偏移、大小、少量反汇编片段。
2. **测试向量。** 补齐当前套件没覆盖的边界情况：零长度 payload、最大头部尺寸、
   正好在 0x6C 边界的容器、多 sector 或异常 block shift 的 MPQ、
   原型嵌套很深的 Lua chunk。
3. **跨平台。** 任何在没有 `bcrypt.dll` 的平台、较老的 Python、或非 UTF-8 locale 下会坏的地方。
4. **反编译质量。** 如果 unluac 把某个结构渲染错了，而你能说明字节码到底是什么，
   一份有记录的绕行方案（就像那个最终写进 `docs/luac-format.md` 的例子）非常受欢迎。
5. **工具与文档。** README 里描述的 CASC 扫描器没有包含在仓库里；
   一个干净、无依赖的实现会是实打实的补充。
6. **性能。** 13 MB payload 上的纯 Python AES 是慢路径。更好的与指令集无关的做法、
   或更快的 xorshift 内层循环都欢迎 —— 前提是不改变结果。

**不**需要的：纯格式化的 PR、没有行为理由的依赖升级，
以及任何让「再分发游戏素材」变得更容易的功能。

## 开发环境

需要 Python 3.8 或更高。核心工作不需要装别的东西。

```bash
git clone https://github.com/mythic-p/w3xd-toolkit
cd w3xd-toolkit
python -m unittest discover -s tests -t .        # 53 个测试，一秒内跑完
```

如果你更习惯 `pytest` 也可以（`pip install pytest && pytest`），
但测试套件必须始终能在纯 `unittest` 下跑通 —— 那是基线。

要验证反编译这条路，还需要 Java 和 unluac：

```bash
scripts/get-unluac.sh          # Linux/macOS
scripts\get-unluac.ps1         # Windows PowerShell
```

开发和测试本仓库的任何东西都**不需要**安装魔兽争霸 III。
如果你想拿真实数据验证改动，请用你自己的副本，并把结果留在仓库之外。

## 代码风格

没有需要满足的 linter 配置；风格就是现有文件的样子。

* **文档字符串解释「为什么」，不是「是什么」。** `# 读取长度，然后读数据` 是噪音。
  值得写的注释是那些记录非显然决定的地方 —— 为什么哈希表索引用 hash type 0、
  为什么忽略 Adler-32、为什么长度有时一字节有时九字节。
* **引用证据。** 当代码实现的是逆向出来的格式时，说明它来自哪里：
  在模块文档字符串里写 RVA，或引用 `docs/` 下的文档。
* **模块保持小而单一。** `w3xd/xorshift.py` 只做一件事。
  宁可新增模块，也不要往已有模块里堆。
* **出错要响。** 错误输入应当抛异常（`W3xdError`、`LuaChunkError`），
  而不是返回 `None` 等着以后被发现。
* **不要有会改变结果的静默回退。** 从 CNG 回退到纯 Python 没问题，因为两者产出完全相同的字节；
  从「这个 chunk 我看不懂」回退到「先输出点什么」不行。
* 行长约 90，四空格缩进，snake_case，用 `from . import x`。
* 每个包的公开接口写进 `__all__`。

## 为格式改动补测试

照 `tests/test_container.py` 和 `tests/test_mpq.py` 的模式来：先把东西造出来，再断言能读回来。

对容器，`w3xd.container.build()` 可以围绕任意字节、按指定 license 合成一个 `.w3xd`：

```python
from w3xd.container import Container, build

raw = build(0x0123456789ABCDEF, fake_mpq())     # fake_mpq 以 MPQ\x1a 开头
c = Container(raw)
assert c.license == 0x0123456789ABCDEF
assert c.decrypt_payload() == fake_mpq()
```

对 MPQ，`tests/test_mpq.py::build_mpq` 从零铺出头部、哈希表、块表和 sector 数据 ——
需要更多成员或不同 sector 大小时扩展它即可。

对字节码，`luac53.chunk.ChunkWriter` 两种风格都能写，所以一次往返长这样：

```python
w = ChunkWriter(chunk.BLIZZARD)
w.byte(1)
w.write_function(my_proto)
data = bytes(w.out)
out, _ = chunk.convert(data)
_h, _n, main, _s = chunk.parse(out, chunk.STOCK)
assert main["consts"] == my_proto["consts"]
```

两个值得从现有套件里学来的习惯：

* **反向用例也要断言** —— 随机数据要抛异常、错密钥要认证失败、被篡改的 payload 要被拒绝。
  一个「什么都接受」的解析器能通过只有正向用例的测试。
* **断言尺寸算术** —— `hdr_size + payload_size + 0x40 == 文件大小` 很便宜，
  却能抓到布局代码里的差一错误。

## 报告格式错误

如果你发现文档里某个字段是错的，开 issue 和提 PR 一样受欢迎。
请把描述写成「任何人**不需要**拷贝游戏文件就能复现」的形式：

* 是哪篇文档的哪个字段；
* 你实际观察到的偏移和大小；
* 你是怎么观察到的（几行反汇编、该字段的 hexdump，或一个合成复现）；
* 你原本以为是什么。

**不要**附带地图、导出的文件或反编译出的脚本。如果证据来自你自己容器里的某个值，
请描述它的**作用与大小**，而不是值本身 —— 尤其是 license，任何时候都不要粘贴。

## 提交与 PR

* 从 `main` 切分支，分支名体现改动（`fix/trailer-size-check`、`docs/mpq-locale-field`）。
* 一个 PR 只做一件逻辑上的事。格式化修正和行为改动不该在同一个提交里。
* 提交信息：简短的祈使句标题，不明显的话在正文说明**为什么**。
  `Fix off-by-one in the sector offset table check` 好过 `fix bug`。
* PR 里说明你改了什么、以及你凭什么认为它是对的。如果涉及格式，链接你更新的文档。
* 请预期评审会要证据。这个项目的全部价值就在于「它的结论是可核查的」，
  所以「我这儿能用」不够 —— 要么给测试，要么给引用。

当干净检出下 `python -m unittest discover -s tests -t .` 通过、改动有测试覆盖、
文档与代码仍然一致时，PR 就算就绪。

## 文档

README 有两种语言：

| 文件 | 语言 |
|---|---|
| `README.md` | 英文（默认） |
| `README.zh-CN.md` | 简体中文 |

**改了一个就要改另一个**，并保持各自第 3 行的语言切换入口完好。
`CONTRIBUTING.md` 与 `CONTRIBUTING.zh-CN.md` 同理。

`docs/` 下的参考文档只有英文；欢迎翻译但不强制，而且**过期的翻译比没有更糟**。

当你落地一个格式改动时，请在同一个 PR 里更新 `docs/` 下对应的文档。
`docs/reverse-engineering.md` 还维护着一份「走不通的路」清单 —— 往里添一条，
能给下一个人省下实打实的时间。
