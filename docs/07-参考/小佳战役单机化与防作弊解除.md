# 小佳战役单机化与防作弊解除

适用范围：KK/KKWE 战役、使用 `DzAPI_Map_HasMallItem` 的商城/防作弊分支、
跨章节 `InitGameCacheBJ` 缓存、宠物许可清理、隐藏难度哨兵，以及小佳
（`小佳`）系列战役的其他变体。

本文是分析方法和可复用原语目录，不是可以直接套到所有小佳地图上的通用补丁。
每张小佳地图都必须有独立的、按源文件 SHA-256 锁定的地图级补丁包。别的
地图中的 key、单位 ID、任务项、章节流程和缓存块不能假定相同。

## 1. 总原则

不要把所有商城 key 一律返回 `true`。

正确策略是：

1. 未识别的 key 默认返回 `false`；
2. 只把真实商城兑换物、正常玩法证据充分的 key 放入白名单；
3. 已知防作弊、删英雄、删 BOSS、清场、跳章 key 放入黑名单；
4. 危险动作按“动作级”中和，不能反转外层剧情条件；
5. 所有修复模块都必须有 `patch()`、`verify()`、静态构建校验和单元测试。

## 2. 商城 key 分类

扫描全战役脚本中的所有 `HasMallItem`，记录：

- 比较方式：`== true`、`!= true`；
- 所属函数、触发事件；
- 对应 WTS 提示；
- 分支中的单位、物品、科技 ID；
- 是否伴随 `RemoveUnit`、`CustomVictory`、`CustomDefeat`、结束游戏或定时器；
- 是否读写跨章节缓存。

商城 key 通常分以下类型：

| 类型 | 典型代码 | 离线策略 |
|---|---|---|
| 核心进度 key | GO/任务完成要求 key | 通常 true |
| 商城兑换物 key | 拾取兑换物后创建宠物/神器 | 对真实兑换物开放 true |
| 商城被动/礼包 key | 加属性、改配方、给资源 | 可选，默认 false |
| 反向进度标记 | `key != true` 时完成正常任务 | false |
| 防作弊标记 | true 时警告、清场、删英雄、跳章 | false |
| 皮肤/缓存 key | 控制英雄形态缓存 | 逐块检查副作用 |

## 3. 从商店反推白名单

必须解析真实 `usei` 库存和兑换物拾取触发器：

```text
商城兑换物 ID -> 物品名称 -> HasMallItem key -> 奖励单位/物品
```

注意：

- 野战值商店、金币商店不一定调用商城 API；
- 真正的商城兑换点通常有 10～20 个固定兑换物；
- 同一个 key 可能既有正常奖励分支，也有防作弊分支；
- 只开 key 不会凭空生成兑换物，还需要商店或领取入口。

## 4. 不要用通用启发式决定 true

扫描器看到：

```jass
if HasMallItem(Player(0), "KEY") != true then
```

不能直接推断“为了让条件通过，应返回 true”。小佳战役大量使用这种结构
检测“没有该防作弊标记”，正确返回值通常是 false。

有明确战役 profile 时：

- 显式白名单优先；
- 自动防作弊黑名单仍保留；
- 未知 key 默认 false；
- 同一 key 不能同时出现在白名单和黑名单。

## 5. 最关键的实现规则：中和动作，不反转条件

错误做法：

```jass
if HasMallItem(Player(0), "KEY") != true then
    // 正常任务更新
else
    // 警告
    ForGroupBJ(玩家全部单位, 删除回调)
endif
```

把外层条件改成 `if false then` 后，会跳过正常任务分支并强制进入 else，
可能导致：

- 反作弊提示；
- 任务项不完成；
- 主角或宠物被删；
- GO 无反应。

正确做法是保留原条件，只替换危险调用：

```jass
if HasMallItem(Player(0), "KEY") != true then
    // 正常任务更新继续执行
else
    call DoNothing() // 清场已禁用
endif
```

只处理 `ForGroupBJ` 玩家全部单位且回调为 `RemoveUnit(GetEnumUnit())`
的分支。删除敌方单位、电影收尾清场等剧情动作不能误伤。

## 6. 常见故障与定位

| 症状 | 常见原因 | 处理 |
|---|---|---|
| 进图后立即回章节页 | 平台等级/哨兵分支 | 固定地图等级，禁用哨兵退出 |
| GO 没反应 | GO 条件含商城 key，或任务项未完成 | 删除命令条件中的商城判断，追踪任务项 |
| 任务更新但 F9 未完成 | 完成的是错误任务项，或前置任务项为空 | 以 GO 条件实际检查的 questitem 为准 |
| 主角物品落地、主角消失 | 坏缓存恢复成非英雄占位单位 | 恢复后校验类型并迁移物品 |
| 宠物或全队几秒后消失 | 商城许可清理 `ForGroupBJ` | 中和具体清场调用，保留正常分支 |
| BOSS 未出现 | true key 设置科技后删 BOSS，或开场定时删除 | 关闭 key 或精确删除 BOSS 删除动作 |
| 终章动画后章节页黑屏 | 电影模式/滤镜/雾效未在 Victory 前恢复 | Victory 前统一恢复 UI 和环境状态 |

## 7. 缓存传递

不能把所有 key 控制的 `SaveGameCache` 块整体改成 true。

只有纯缓存块可以解除条件：

- `InitGameCacheBJ`
- `StoreUnitBJ`
- 缓存元数据 `StoreInteger`
- `SaveGameCache`
- 安全的局部变量赋值

若块中包含以下任一操作，必须保留原条件：

- `RemoveUnit` / `KillUnit`
- `CustomVictoryBJ` / `CustomDefeatBJ`
- `SetNextLevelBJ`
- 长时间 `TriggerSleepAction`
- 其他剧情或战斗副作用

正常章节末尾通常另有无条件缓存保存，因此不要让带副作用的付费分支强制执行。

## 8. 小佳战役已验证危险 key 示例

以下只是模式示例，其他战役必须重新验证：

- `WS6S6S`：占位英雄缓存或删英雄；
- `Y55TT`、`SSD99R`：全局清场；
- `YSZT`：设置 `R60G` 后可删除主线 BOSS；
- `YEZ500`：真实野战值奖励与反作弊/关键单位分支冲突；
- `T6DS`、`SX015`、`SSE660`、`QQ5564R`：警告、删英雄或防作弊；
- `J5T6R`、`H6RDNN`：正常完成通常要求 false 的进度标记。

## 9. 高数值不等于 x100

后期 BOSS 的几十万生命、四位数混乱攻击可能完全是对象数据设计。

先比较：

- `uhpm`
- `ua1b` / `ua2b`
- 英雄等级和三维
- 玩家 handicap
- 难度分支
- 运行时最大生命/攻击加成

只有运行值达到对象数据约 100 倍、出现异常 handicap 或重复加成调用时，
才应怀疑 x100 后手。

## 10. 第 19 章终章黑屏案例

已观察到的结尾结构：

- 开场调用 `CinematicModeBJ(true, GetPlayersAll())`；
- 多条电影滤镜和雾效切换；
- 正常结尾最后只显示文字、等待 10 秒，然后调用 `CustomVictoryBJ`；
- `EVENT_PLAYER_EVENT_END_CINEMATIC` 跳过路径也会直接调用 `CustomVictoryBJ`；
- 没有在返回章节页前统一执行 `CinematicModeBJ(false)` 和
  `DisplayCineFilter(false)`。

结论：黑屏很可能不是战役数据损坏，而是离开最后一章时电影模式或滤镜状态
仍被保留。应在正常结尾和跳过结尾两条路径的 `CustomVictoryBJ` 前统一恢复：

```jass
call CinematicModeBJ(false, GetPlayersAll())
call DisplayCineFilter(false)
call FogMaskEnable(true)
call FogEnable(true)
```

雾效/UI 恢复必须放在 Victory 之前，不能只在 Victory 后调用。

## 11. 独立地图补丁包与共享流水线

KK 单机化工具应分成两层：

- **共享框架**：解析、构建、pjass、Doctor、Storm、哈希校验和经过验证的
  通用原语；
- **地图插件**：每张小佳地图单独维护的 key 白名单/黑名单、章节规则、
  精确修补脚本和测试。

不能把某一章的防作弊处理当成“小佳系列通用规则”。每个新源文件都必须建立
独立插件，按源 SHA-256 自动选择；没有匹配插件时应停止并先分析，而不是
套用上一张图的 profile。

建议结构：

```text
campaign_plugins/<campaign-slug>/
  manifest.py 或 manifest.json
  key_policy.py
  chapter_rules.py
  patches/
  tests/
```

manifest 至少记录：

- 源 `.w3n` SHA-256、标题、章节顺序；
- 已验证为 true/false 的商城 key；
- 每章的哨兵、BOSS、缓存、任务项和命令规则；
- 补丁执行顺序；
- 构建后必须消失的危险指纹；
- 需要用户执行的运行时测试点。

当前共享脚本修复模块位于 `tools/war3map-injector/`，由
`campaign_singleplayer.py` 的 `patch_chapter_script()` 调用。它们可以在新
地图中作为候选原语使用，但只有地图插件明确选用并验证后才算该图的修复：

| 模块 | 作用 |
|---|---|
| `_patch_anticheat_markers.py` | 识别防作弊 WTS 与商城负标记 |
| `_patch_command_mall_guards.py` | 移除 GO 等进度命令中的商城条件 |
| `_patch_chat_registration.py` | 修复初始化阶段聊天命令注册 |
| `_patch_chat_gate.py` | 修复聊天输入门禁 |
| `_patch_cache_flags.py` | 清除跨章节进度污染标记 |
| `_patch_cache_handoff.py` | 修复纯缓存传递、禁用伪英雄缓存 |
| `_patch_restore_guards.py` | 校验/补建恢复后的主角、副角、宠物 |
| `_patch_mall_cleanup.py` | 中和商城许可证导致的全队删除 |
| `_patch_mall_wipe.py` | 兼容旧式福利整队清理 |
| `_patch_pet_delete.py` | 兼容旧式宠物/英雄删除块 |
| `_patch_sentinel_exits.py` | 禁用等级、重复物品等哨兵退出 |
| `_patch_critical_props.py` | 修复关键单位死亡软锁 |
| `_patch_region_drain.py` | 收窄区域清场 |
| `_patch_drops.py` | 修复掉落触发器提前失效 |
| `_patch_hero_death.py` | 只允许主角死亡触发失败 |
| `_patch_unlock.py` | 任务解锁兜底 |
| `_patch_cinematics.py` | 电影/跳过流程修复 |
| `_patch_final_cinematic_cleanup.py` | 终章 Victory 前恢复电影模式、滤镜和雾效 |
| `_neutralize_ends.py` | 中和平台专属胜负结束调用 |
| `_gate_scan.py` | 静态扫描致命平台门禁 |
| `_campaign_profiles.py` | 战役级 true/false key 数据策略 |
| `stub_platform_natives.py` / `_stub_inplace.py` | 平台原生函数离线存根 |

后续新增地图或后手时的固定结构：

1. 先建立该源 SHA 的独立 campaign plugin；
2. 在地图插件中列出本章节的精确危险分支；
3. 如确属可复用代码形态，再提取独立 `_patch_xxx.py` 原语；
4. 地图插件按顺序显式调用所需原语；
5. 提供该地图专属 `patch()`、`verify()` 和测试；
6. 新源文件没有插件时停止，不自动套用其他地图规则。

共享原语要求幂等、模式明确、同时具备正向和反向测试。某张图验证成功的
补丁不能自动升级为下一张图的通用规则。

## 12. 发布检查

- 所有商城 key 都有明确分类；
- 无活动中的玩家全队许可清理；
- GO 条件不含商城判断；
- 纯缓存传递存在，带副作用缓存块保持 gated；
- 每个模块有正向和反向测试；
- pjass 通过；
- Map Doctor 1.27 与 Reforged 通过；
- Storm 能打开全部章节；
- MPQ 平台标志为 0；
- 战役内每个章节回读字节一致；
- 两份部署文件 SHA-256 一致；
- 运行测试由用户执行，自动化不启动游戏。
